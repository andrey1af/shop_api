# Архитектура Shop API

Интернет-магазин бытовой техники: витрина и админ-панель в браузере, REST API,
сервис авторизации и генератор событий об изменении товаров.
Всё запускается через Docker Compose (`make up` в каталоге `src`).

Схемы баз данных — в [database.md](database.md).

## Сервисы

![Архитектура Shop API](images/architecture.png)

Исходник — [diagrams/architecture.puml](diagrams/architecture.puml), картинка пересобирается командой `make diagrams`.

| Сервис | Назначение | Хранилища | Порт на хосте |
|---|---|---|---|
| `web` | nginx: статика фронтенда, прокси `/api/v1/*` и SSE в api | — | 3000 |
| `api` (api-service) | REST API магазина, рассылка обновлений по SSE, приём событий из Kafka | Postgres `shop_api`, Redis | 127.0.0.1:8090 |
| `auth` (auth-service) | регистрация, вход (в т. ч. OAuth), сессии, access/refresh-токены; доступен только по gRPC | Postgres `shop_auth` | 127.0.0.1:50051 |
| `image` (image-service) | хранение фото товаров с шардированием по id; доступен только по gRPC | Postgres `shop_images_1..4` | 127.0.0.1:50052 |
| `generator` (generator-service) | раз в 2 с меняет цену и остаток случайного товара и публикует событие | — | — |
| `kafka` + `kafka-init` | брокер событий; `kafka-init` создаёт топик `product.updates` | — | — |
| `redis` | кэш содержимого фото товаров | — | — |

У каждого Go-сервиса своя база данных: другой сервис не читает её напрямую,
а обращается через API владельца (api-service к auth-service и image-service —
по gRPC, генератор к api-service — по REST).

## Устройство Go-сервисов

Все Go-сервисы устроены по Clean Architecture: зависимости направлены
внутрь, к бизнес-логике.

- **usecase** содержит все бизнес-правила (валидация, проверки остатков,
  ротация токенов); репозитории только читают и пишут данные.
- **Порты** объявляет тот, кто их использует: например, `ProductUpdateNotifier`
  объявлен в usecase api-service, а реализован пакетом `broadcast`.
- Общие ошибки сервиса лежат в `internal/errors`.
- SQL-запросы описаны в `internal/database/queries`, Go-код по ним
  генерирует sqlc (`make sqlc-gen`); миграции — goose, отдельный образ `migrator`.
- gRPC-контракты — `api/proto/auth/v1/auth.proto` и `api/proto/image/v1/image.proto`,
  стабы генерируются в `backend/gen` (`make proto-gen`).

## Авторизация

Пользователь входит через api-service, который проксирует вызов в
auth-service по gRPC. Каждый вход создаёт **сессию** в БД auth-service и
выдаёт пару токенов:

| Токен | Формат | Срок | Где хранится у браузера |
|---|---|---|---|
| access | JWT (HS256): `id`, `email`, `sid` (id сессии), `jti`, `iat`, `exp` | 15 мин (`JWT_TOKEN_TTL`) | `localStorage` |
| refresh | 32 случайных байта (base64url), в БД — только SHA-256 | 30 дней (`REFRESH_TOKEN_TTL`) | cookie `refresh_token`: `HttpOnly; SameSite=Strict; Path=/api/v1/auth` (+ `Secure` в проде) |

Access-токен действителен, только пока активна его сессия, поэтому отзыв
сессии мгновенно «выключает» и access, и refresh. Middleware api-service
проверяет токен в auth-service (`ValidateToken` по gRPC) на каждом запросе
к защищённым ручкам.

### Обновление токенов и обнаружение кражи

Refresh-токен одноразовый: обмен выдаёт новую пару и продлевает сессию,
а старый токен помечается использованным. Если кто-то предъявит уже
использованный токен — значит, токен скопирован: отзывается вся сессия.

### Когда отзываются сессии

| Действие | Ручка | Что отзывается |
|---|---|---|
| Выход | `POST /api/v1/auth/logout` (по refresh-cookie или access) | текущая сессия |
| Выход со всех устройств | `POST /api/v1/auth/logout-all` | все сессии пользователя |
| Смена пароля | `POST /api/v1/auth/change-password` | все сессии, кроме текущей |
| Сброс пароля | `POST /api/v1/auth/reset-password` | все сессии |
| Повтор использованного refresh | `POST /api/v1/auth/refresh` | сессия этого токена |

auth-service раз в `SESSION_CLEANUP_INTERVAL` (1 ч) удаляет истёкшие сессии
и refresh-токены; использованные refresh-токены хранятся 7 дней — столько
работает обнаружение их повторного использования.

Клиенты без браузера (генератор, k6) получают refresh-токен
в теле ответа и могут передать его в `POST /auth/refresh` JSON-ом
`{"refresh_token": "..."}`.

## Изменения товаров в реальном времени

generator-service публикует событие в Kafka (`product.updates`), api-service
читает его, обновляет товар в `shop_api`, рассылает его подписчикам SSE
и коммитит offset.

- **Порядок.** Ключ сообщения — `product_id`, поэтому события одного товара
  попадают в одну партицию и обрабатываются по порядку.
- **Доставка — at-least-once.** Offset коммитится после обновления БД;
  событие несёт абсолютные значения, поэтому повтор безопасен. Невалидные
  сообщения пропускаются, временные ошибки повторяются с backoff.
- **SSE.** `GET /api/v1/sse/products`; браузерный `EventSource` не умеет
  слать заголовки, поэтому для этой ручки токен можно передать в
  `?access_token=` (nginx пишет в журнал путь без query). Сервер шлёт пинг
  каждые 15 с; хаб живёт в памяти одного экземпляра api.
- Покупка товара (`PATCH /products/{id}/stock`) тоже рассылается по SSE.
- **Витрина.** Каталог обновляет цену и остаток в карточках на лету и
  показывает над сеткой ленту последних 20 изменений (было → стало) с
  индикатором подключения к потоку (`assets/js/live.js`, `live-feed.js`).

## Фото товаров

Сами фото хранит отдельный **image-service**; api-service ходит в него по
gRPC (`api/proto/image/v1/image.proto`). Связь с товаром — только
`products.image_id` в `shop_api`; id фото генерирует api-service.

**Шардирование.** У image-service четыре строки подключения
(`DB_SHARD_1_URL` … `DB_SHARD_4_URL`) — пока это четыре базы на одном
сервере Postgres `image-db`. База выбирается по первому символу строкового
представления id: `0-3` → первая, `4-7` → вторая, `8-b` → третья, `c-f` →
четвёртая. id — случайный UUID v4, поэтому фото ложатся по шардам
равномерно. Схема у шардов одинаковая, миграции `image-migrate` применяет
к каждому по очереди. Чтобы вынести шард на отдельную машину, достаточно
поменять его строку подключения.

Содержимое кэшируется в Redis на стороне api-service (cache-aside, ключ
`image:{id}`, TTL 1 ч, файлы больше 5 МБ не кэшируются); замена и удаление
картинки сбрасывают ключ. Связь с товаром всегда проверяется в Postgres,
поэтому удалённый товар не отдаёт фото из кэша. Если Redis недоступен,
фото читаются из image-service. Фото передаётся одним gRPC-сообщением,
поэтому лимит сообщения поднят до 25 МБ (`IMAGE_GRPC_MAX_MESSAGE_BYTES`).

## Структура репозитория

```
src/
├── api/proto/            gRPC-контракты
├── backend/
│   ├── api-service/      REST API, SSE, consumer Kafka
│   ├── auth-service/     авторизация (gRPC)
│   ├── image-service/    фото товаров, 4 шарда Postgres (gRPC)
│   ├── generator-service/
│   └── gen/              сгенерированные gRPC-стабы
├── frontend/             nginx + статика витрины и админ-панели
├── docs/                 эта документация
├── compose.yaml          dev-стек (подключает compose-файлы сервисов)
└── compose.prod.yaml     прод-стек
```
